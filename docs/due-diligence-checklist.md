# Due-diligence checklist sources

Checked live on 18 October 2026. Before this change every item on a listing came back "?" because the crawl never reached the registers: DAWA answers `410 Gone`, the Datafordeler DAR fallback query was invalid (`adgangspunkt` has no subfields, `adresseringsvejnavn` is not a filter field), so no listing got a husnummer, so BBR was never asked. Noise had no configured layer and the soil endpoint answered HTTP 406. In the database: 0 of 990 listings had BBR data, 4 had a noise value.

## Choices and limits

- **Noise uses the EU mapping layers (2017 rail, roads undated/2020), not the 2022 Danish Nord2000 maps.** The 2022 maps are only reachable through MiljøGIS's own map process, which took 12 to 37 seconds per layer and up to 6.7 MB per answer in the same test. The EU layers cover the four largest towns (including Aalborg) and major roads and railways everywhere; smaller roads outside those towns are not mapped, which the checklist's source line says. The listing page's separate noise panel still shows the 2022 maps.
- **Soil is the address point, not the whole parcel.** A parcel mapped only away from its address point reads as clear, so the source line keeps the map link.
- **The oil tank answer uses the tank register as well as the heating.** An earlier version of this page said `BBR_TekniskAnlaeg` could only be filtered by its own id. The schema's `@filterRequirement` says one of `id_lokalId`/`datafordelerRowId` or one of the temporal arguments, which is the same directive `BBR_Bygning` carries and which that lookup already satisfies with `registreringstid`/`virkningstid`. The filter takes `husnummer`, `bygning`, `grund` and `tek020Klassifikation`, and `in` on strings, so tanks are asked three ways (husnummer, the husnummer's buildings, its grunde) and merged on `id_lokalId`, because the filter has no `or` and BBR hangs a tank off whichever of the three its registrant used. Any of the three failing fails the source: "no tanks" never means "one query did not answer".
- **What the tank register cannot say.** Classification 1110 is "tank"; the content code (`tek034`) needs BBR's code list, which was not reachable, so a tank is worded as a tank, not as an oil tank, and the content, placement and decommissioning-method codes are carried raw. A tank counts as decommissioned when it has a decommissioning year (`tek072`) or method (`tek028`), or a status other than "Opført". Tanks from before registration can be missing and a removed tank can stay registered, so an empty list is "none registered", never "none", and with the heating unknown it still leaves the answer unknown.
- **MAT restrictions use the area, not the extent text.** A parcel carries fredskov, strandbeskyttelse or klitfredning when its `*_areal` is above zero. The `*_omfang` text is not read, because its vocabulary is not in the schema and a guessed "none" value would put a warning on a parcel without one. Jordrente is not used for the same reason; majoratsskov is a number, so its presence is enough. `landbrugsnotering` is an enumeration (Familiebrug, Landbrug, Landbrug uden bygning), so any value means a duty to farm.
- **MAT and VUR are both found through the BFE.** The address register no longer returns a parcel, so the husnummer's BFE is found once through BBR (`BBR_Grund` to `BBR_Ejendomsrelation`) and shared by both lookups for ten minutes, concurrent callers included. A BFE a caller already holds (stored by an earlier crawl) is used as it is, as before. Both are houses only: an apartment's BFE is its own, and the parcel's BFE would return the whole building's land and valuation.
- **Versions.** MAT is `v3` and VUR `v2`, from Datafordeler's GraphQL pages for each. The client walks to an older version only on HTTP 404, and `DATAFORDELER_MAT_VERSION` / `DATAFORDELER_VUR_VERSION` pin one. The listing page's cadastral panel (`cadastral/source.ts`) still calls `MAT/v2` and `Flexible/v2` directly and was not changed.
- **Stored rows heal within a week.** The new `land` and `oil_tanks` sources are recorded in `source_status` but are not in `enrichment-refresh`'s register list, so a listing is not re-enriched on every crawl for want of them (an apartment never has land or a parcel valuation). Rows pick them up at the seven-day refresh, or on the next change.
- **Verifying live.** Run the "Discover Datafordeler schema and files" workflow. It now prints the tank classification and code distributions for municipality 0851, which of `husnummer`, `bygning` and `grund` tanks carry, whether each of the three filters answers, and a MAT probe for one BFE.
- **Listing pages show live answers.** The page's register lookup now builds the flags for listings too, and each item takes the live answer when there is one and the crawl's stored answer otherwise (`mergeRiskFlags`).
- **Stored rows heal on the next crawl.** `enrichmentNeedsRefresh` already re-enriches a listing whose register status is not `real`, so every listing the crawl sees gets the new answers. The crawl also no longer overwrites a stored husnummer, matrikel or BFE with null when this run's lookup fails.
