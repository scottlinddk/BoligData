# BoligData

**BoligData** (Danish) / **BoligDataResearch** (English) — a research and due-diligence dashboard for Danish property investors and advisors. Looks up Danish addresses in the public registers (DAR, BBR, MAT, VUR and others) and surfaces a structured due-diligence checklist per property. It does not scrape listing portals; see "Data sources" below.

The UI is fully bilingual (Danish default, English) and ships with light and dark themes; both preferences persist in `localStorage`.

Search now uses the supplied photo-led design reference: a white/navy/blue palette, compact filters, a split listing/map layout and a charcoal footer. Draw an area with clicks or taps to filter listings; boundaries persist in URLs and saved searches. Spatial matching runs before counts and pagination.

## Stack

## Data sources

**No listing portal is scraped.** Boligsiden's data policy prohibits scraping, crawling and data mining without a written agreement, and a Danish court has held that such a policy notice is enough to reserve database rights (BoligPortal v. ReData). The earlier Boligsiden and Boliga crawlers, their derived market statistics and the price-by-time-on-market feature have been removed. Do not add a portal scraper without a written agreement with the portal or broker concerned.

Data comes from the public registers and open statistics below, looked up on demand for an address a signed-in user enters or has saved. Danmarks Statistik (StatBank) provides regional context.

**Mock is opt-in, not the default.** Each flag is read at call time and only serves fabricated data when explicitly set to `"true"`; the old `!== "false"` convention meant an unset flag silently invented register data, which is how `/api/property-lookup` came to return mock matrikelnumre and valuations in production. A source that can't reach its register now reports itself unavailable and its fields come back `null`.

- **Address/cadastral** (`address-lookup.ts`): Dataforsyningen's address API (DAWA, `https://api.dataforsyningen.dk/adgangsadresser`), **open data, no credential** — the one source that returns real data on a deployment with no Datafordeler key at all. One request resolves the DAR husnummer UUID, `matrikelnr`, `ejerlav` (name + code) and the access-point coordinates; an exact `q=` search falls back to a single fuzzy retry. A second request follows the record's link to `/jordstykker/<ejerlavkode>/<matrikelnr>` for the parcel's **BFE-nummer**, which the adgangsadresse itself does not carry and which is the key VUR indexes valuations by; that request is failure-isolated, since it is supplementary to an otherwise good address resolution. Two mapping details verified against a live response (2026-08-01) and pinned by the tests: DAWA orders coordinates `[lon, lat]`, and **`zone` is retired** — it answers the literal `"Udfaset"` for every address, so `properties.zone` now needs a different source (Plandata's zonekort) rather than a mapping fix. The lookup also doubles as the **geocoder** — callers that pass only an address get real coordinates back, which is what the noise lookup is given instead of the `0,0` it used to receive. Resolves `properties.id_lokalid`/`matrikelnr`/`ejerlav`/`bfe_nummer` for saved properties (migrations 010, 021). Sunset: DAWA closed 2026-08-17 — already past. Per the 2026-08-22 [ChatGPT-plan reconciliation](docs/chatgpt-plan-reconciliation.md), `lookupAddressCadastral` now falls back to a Datafordeler DAR GraphQL lookup (`address-lookup-dar-fallback.ts`) when DAWA's search fails and `DATAFORDELER_API_KEY` is set, reusing the same GraphQL client/version-walking/schema-introspection helpers `bbr.ts` already relies on. DAR has no fuzzy free-text search, so the fallback parses the address into street name + house number (+ postal code) and filters DAR's `Husnummer` entity by those. **Narrower than DAWA by design**: the fallback resolves identity and geocoding (`idLokalid`/`lat`/`lon`/`postalCode`/`municipalityCode`) — enough to unblock BBR/VUR/noise/sales, which all key off the husnummer UUID or coordinates — but not `matrikelnr`/`ejerlav`/`bfeNummer`/`zone`, which would need a spatial join against Matriklen's parcel geometry this repo doesn't do yet; those stay `null` rather than being guessed. Every `AddressCadastral` carries `resolvedVia: "dawa" | "dar_fallback"`, surfaced in `/api/property-lookup`'s `sources[]` register label. **Not verified live** — this sandbox has no network egress to `dataforsyningen.dk`/`datafordeler.dk`, so neither DAWA's actual current status nor the fallback's DAR field-name guesses could be confirmed directly; see "Manual follow-up steps" below.
- **Soil type** (`geus-jordart.ts`): GEUS Jordartskort, no auth. Supplementary context only (permeability/radon), never authoritative for contamination status.
- **Soil contamination** (`miljoeportalen-v1v2.ts`): Danmarks Miljøportal's V1/V2 "Forurenede grunde" registry, expected no auth — endpoint/layer name not yet verified against live docs (403'd automated research fetches). Authoritative source for the due-diligence checklist's "no marking for soil contamination registered" vs. V1/V2 status.
- **Jordforureningsattest** (`jordforureningsattest-link.ts`): pure derivation like `tinglysning-link.ts` — builds a deep link to the parcel's soil contamination certificate on `jord.miljoeportal.dk/report/?elav=<ejerlavskode>&matrnr=<matrikelnr>`. Needs the numeric ejerlav *code* (not the name), which `address-lookup.ts` now also resolves from DAR (`ejerlav.kode`); stored as `riskFlags.soilContaminationAttestUrl` and linked from the due-diligence checklist's soil item.
- **Encumbrance** (`tinglysning-link.ts`): tinglysning.dk (the Danish land register) has no open API, so this stays a pure derivation — builds a deep link from `matrikelnr`/`ejerlav` so an advisor can pull the real tingbogsattest themselves, rather than an automated true/false.
- **BBR** (`bbr.ts`): Datafordeler's entity-based GraphQL service, reached by starting at **DAR's `Husnummer` entity and traversing to BBR via `husnummerGiverAdgangTilBygning`** (`https://graphql.datafordeler.dk/DAR/<version>`) rather than querying `BBR_Bygning` directly — the only key this pipeline holds for a property is the DAR husnummer UUID that `address-lookup.ts` resolves, and BBR's Bygning entity isn't queryable by it, but the traversal is. Requires `DATAFORDELER_API_KEY` (set in Vercel); auth is an API key query parameter — the REST-style "tjenestebruger" username/password login only works for fetching the GraphQL schema, not for querying entity data. The **version segment is not pinned**: registers are versioned independently and withdrawn versions answer `HTTP 404`, which is exactly what happened when DAR moved off `v1` — every listing reported BBR as unavailable, quoting a 404 (and, before the URL was redacted, the deployment's API key with it). `datafordeler.ts` now walks the known versions newest-first and remembers the one that answers; `DATAFORDELER_DAR_VERSION` pins one when that is wanted. Three things the query shape gets right that the earlier version did not: the bitemporal `registreringstid`/`virkningstid` arguments are sent where the register has them and **dropped on the retry** when it answers "the argument `registreringstid` does not exist" (they exist on DAR/BBR, not on VUR), BBR's field names are **ASCII-transliterated** (`byg026Opfoerelsesaar`, not `byg026Opførelsesår` — GraphQL rejects the whole document on one unknown field, so this alone produced an all-null result), and the UUID/timestamp are inlined as escaped literals instead of typed GraphQL variables, whose type names (`String!` vs `DateTime!`) differ per register. Three further robustness measures: unverified field names are **filtered against the live schema** (`__type(name: "BBR_Bygning")`) before the query is sent, so a wrong guess is dropped rather than rejecting the whole document; the query then still runs a **two-tier retry** — an extended field set first, falling back to the field set verified against Datafordeler's published DAR→BBR example, which covers deployments with introspection turned off — and a husnummer that gives access to several buildings picks the **dwelling by largest residential area**, not `[0]`, which is frequently the garage. Heating is decoded from BBR's real representation, the `byg056Varmeinstallation` + `byg057Opvarmningsmiddel` **code pair**, onto this repo's vocabulary: oil heating is central heating or stoves burning "flydende brændsel", so `oilTankRisk` upgrades from the `buildingYear < 1970` heuristic to a real register read. `enrich.ts` prefers these values over listing-derived guesses whenever the lookup succeeds, and the property detail page surfaces floors/roof/wall material.
- **Noise** (`stoejkort.ts`): Miljøstyrelsens "Støj-Danmarkskortet" (road/rail traffic noise, Lden metric), served via a WFS on `geoserver.plandata.dk` under a "Støjkort" theme group. Miljøstyrelsen states access to that group requires contacting them directly, so this isn't a fully open self-serve endpoint (same shape of blocker as BBR/Datafordeler). The layer name is therefore **configuration, not a default**: `STOEJKORT_TYPENAME` must come from a live `GetCapabilities` response, and until it is set the lookup is skipped and reported as unconfigured. The guessed `noise_map:lden_road_rail` was earning an `HTTP 400` on every listing view — GeoServer's answer to an unknown `typeName`, indistinguishable in the UI from an upstream outage. The request itself is now a valid WFS **2.0.0** `GetFeature` (`typeNames`/`count`, `srsName` and the bbox both named by the `urn:ogc:def:crs:EPSG::4326` URN, whose axis order is **lat,lon** — sending no `version` at all left that to the server's default and quietly decided whether the box landed in Denmark), and the Lden attribute is matched case-insensitively (`STOEJKORT_LDEN_PROPERTY` overrides). `noiseZoneEstimate` stays `null` until a layer is configured, which is the honest answer — `STOEJKORT_MOCK_MODE=true` brings back a synthetic dB value that reads like a measurement, so it belongs in local development only.
- **Sewer separation** (`spildevandsplan.ts`): no unified national API exists for municipal spildevandsplaner (each of Denmark's ~98 municipalities publishes independently), so this stays a pure derivation like `tinglysning-link.ts` — a static lookup table of municipality → spildevandsplan site, scoped to the municipalities within the configured postal-code ranges (`CRAWL_ZIP_RANGES`, default 9000-9900, Region Nordjylland). Always advisory (`sewerSeparationCheckRequired: true`), same as the encumbrance check — an automated true/false per property isn't possible without per-municipality integration.
- **Matriklen** (`matrikel.ts`): Datafordeler's **MAT** GraphQL service (`https://graphql.datafordeler.dk/MAT/v3`), reusing the same `DATAFORDELER_API_KEY` as BBR. BFE number to `MAT_SamletFastEjendom` to `MAT_Jordstykke`, with field names checked against the published schema (the earlier version queried a `Matrikel` register that does not exist). Gives the registered land area (`properties.registered_area_sqm`, migration 012) and, for the due-diligence checklist, fredskov, strandbeskyttelse, klitfredning, majoratsskov and the farmland note. The BFE comes from the address register, a stored identifier or, for a house, from the husnummer through BBR. `MATRIKEL_MOCK_MODE` is off unless set. See [checklist sources](docs/due-diligence-checklist.md).
- **Ejendomsvurdering** (`ejendomsvurdering.ts`, `vur-valuations.ts`): Datafordeler's **VUR** GraphQL service (`https://graphql.datafordeler.dk/VUR/v2`), same `DATAFORDELER_API_KEY`. BFE number to `VUR_BFEKrydsreference` to `VUR_Ejendomsvurdering`, with no schema introspection (Datafordeler switched it off). Resolves `enrichments.public_valuation` (migration 013): latest assessed property and land value and the year, and the year before for the checklist's change figure. Houses only, since an apartment's valuation is keyed by its own BFE. A BFE already held is used as it is; otherwise it is found from the husnummer through BBR.
- **BBR tanks** (`bbr-tanks.ts`): `BBR_TekniskAnlaeg` of classification 1110, asked by husnummer, the husnummer's buildings and its grunde and merged by id. Feeds the checklist's oil tank item: a tank still registered as standing is a warning whatever the heating is. Not verified live; see [checklist sources](docs/due-diligence-checklist.md) and the discover workflow.

**Grunddatamodeller considered but not built**: researching Datafordeler's Grunddatamodellen (grunddatamodel.datafordeler.dk) and Dataoversigt (datafordeler.dk/dataoversigt) for further integration turned up **EJF (Ejerfortegnelsen, the ownership register)** as the highest-value remaining candidate — real registered owner vs. listing agent is a strong due-diligence signal BoligData doesn't have today. It's deliberately not built yet: EJF requires a separate access request to Geodatastyrelsen with **MitID Erhverv + OAuth**, and explicitly cannot be accessed with an API key, unlike every other source in this list. That's a new authorization process, not just a missing credential, so it's a distinct follow-up rather than a `MOCK_MODE` flip.

## Listing recommendations

An advisor or agent can push one or more listings to one or more of their connected clients (search results and the property detail page both expose a "Send recommendation(s) to client(s)" action when signed in as `advisor`/`agent`), with an optional message. `public.listing_recommendations` (migration 014) holds one row per `(property, client)` pair, grouped by `batch_id` for a single send; RLS scopes reads to either party, inserts to the connected advisor/agent, and updates (accept/dismiss + a reply message) to the recipient only. `GET/POST/PATCH /api/recommendations` (`apps/web/api/recommendations.ts`) is the single consolidated endpoint (kept to one file to stay under Vercel's serverless function count limit, same as `notifications.ts`/`favorites.ts`). `RecommendationAlerts` (`apps/web/src/components/recommendation-alerts.tsx`) polls a client's pending recommendations every 30s and renders them as dismissible, actionable toast cards; the full history (sent for advisors/agents, received for clients) lives at `/recommendations`, linked from the main nav.

## Account area: notifications, messages, personal info, settings

Signed-in users get an account area (avatar menu in the header, or the ☰ menu on mobile) with four views under `/account/*`:

- **Notifications** (`/account/notifications`) — the existing search-match feed (migration `008`) widened by migration `015` to a general-purpose, typed feed (`new_listing` / `price_drop` / `message` / `data_update` / `system`), filterable by type, with mark-read/mark-all-read.
- **Messages** (`/account/messages`) — 1:1 buyer↔professional (agent or advisor) chat threads, optionally scoped to a listing. `public.conversations`/`public.messages` (migration `016`) hang off the existing `advisor_connections` pairing — a thread can only be started between two already-connected parties, enforced by RLS. Sending a message writes a `message`-type notification for the recipient via the service-role client (notifications otherwise has no authenticated-insert policy). No websockets: the inbox and open thread poll every 15s, the same pattern `RecommendationAlerts` already used for 30s polling.
- **Personal info** (`/account/profile`) — name/phone/contact-preference/best-time-to-contact, self-service editable. Email is read-only (sourced from the auth session) to avoid wiring Supabase's email-change/re-confirmation flow.
- **Settings** (`/account/settings`) — per-notification-type Email/"Push" (in-app only, no real browser push infra) toggles for everyone; an agent-only Agency profile card (license number, lead routing, notify-on-new-lead); admin-only System notices (site-wide banner toggle, `public.app_settings`, migration `019`) and a "Fetch new listings" card that dispatches `.github/workflows/new-listings.yml` through the GitHub API (needs the `GITHUB_DISPATCH_TOKEN` Vercel env var, see `.env.example`) and shows its latest runs, and a read-only Registered agents directory.

All four resources (profile fields, notification channels, agent config) live on `user_profiles`, added by migration `017`, alongside a `before update` trigger that blocks any non-service-role update to `role`/`organization_name` — closing a latent gap where `user_profiles_update_own`'s RLS policy (migration `001`) had no `with check` and would otherwise have let a signed-in user self-promote via a direct Supabase client call. `GET/POST /api/account?resource=conversations|thread|profile` (`apps/web/api/account.ts`) is one consolidated endpoint, same "stay under Vercel's serverless function count limit" reasoning as `admin.ts`/`notifications.ts` — the project was already at exactly 12 API functions before this feature.

**The 12-function budget is fully spent.** Vercel's zero-config build turns *every file it uploads* under `apps/web/api/` into its own Serverless Function — helpers and `*.test.ts` files included, not just route handlers — and the Hobby plan rejects a deployment at 13 with `No more than 12 Serverless Functions can be added to a Deployment on the Hobby plan`. So a new endpoint means consolidating into an existing handler behind a `?resource=` query param (the `account.ts`/`admin.ts` pattern), never a new file in `api/`. Two guards back this up: `apps/web/.vercelignore` keeps test files out of the upload, and `apps/web/server/api-function-budget.test.ts` fails the test suite the moment `api/` exceeds 12 files or gains a test file — worth having because `.github/workflows/deploy.yml` runs no checks before `vercel build`, so the budget would otherwise only be enforced after a merge to `main`. Tests that exercise a handler live under `server/` and import it across the boundary, as `server/lib/property-lookup/property-lookup.endpoint.test.ts` does.

## Property lookup (screening + scoring inputs)

`GET /api/property-lookup?address=<free-text address>&askingPrice=<dkk>` resolves a Danish address against DAR/BBR/OIS (reusing the existing `address-lookup.ts`/`bbr.ts`/`ejendomsvurdering.ts` enrichment sources rather than duplicating them under a separate `enrichment/dar|bbr|ois` tree), screens it against the six hard house-buying criteria, and returns the raw inputs for the relative (weighted) scoring model. **Open — no `Authorization` header required**, so scripts and the scheduled screening task can call it without minting a browser session. Unlike `/api/properties/:id`, it reads nothing per-caller: the response is a pure function of the query params plus the deployment-wide `SCREENING_*` thresholds, touches no Supabase row, and is identical for every caller, so it is served with the same public CDN caching (`s-maxage=300, stale-while-revalidate=3600`) as the anonymous search response. Two consequences to keep in mind: the configured thresholds are inferable from the screening reasons, and now that the enrichment sources default to live, this **is** an unmetered public path to the `DATAFORDELER_API_KEY` upstream (and to DAWA), throttled only by that cache — put a shared secret or a rate limit in front of it. The response's `sources` array reports, per register, whether each group of values came back `live`, `mock` or `unavailable` and why, and `dataMode` is the worst of the four: read those before trusting any figure in the payload. Those error strings quote the upstream verbatim and are rendered in the listing's "Registerkilder" panel, so `crawl/http.ts` **redacts credential-bearing query parameters** (`apiKey`, `token`, `password`, ...) out of any URL it puts in an error — a Datafordeler 404 was otherwise publishing the deployment's `DATAFORDELER_API_KEY` to every anonymous caller. Rotate that key if it was ever served this way. Optional query params: `postalCode`, `lat`, `lon`, `sellerTakeoverDate`, `totalEncumbrancesDkk`, `roomCount`, `roomCountDefinition` (`A`/`B`/`C`, defaults to `B`), `energyLabel`.

Every field in the response — `screening[]`, `renovationCategory`, `scoringInputs` — carries `source: "ai"`. This is deliberate and permanent: the endpoint never asserts `source: "verified"`, since verifying encumbrances, servitutter, and tilstandsrapport findings stays a human decision it cannot make for the caller.

- **Screening** (`apps/web/server/lib/screening/`): `hard-criteria.ts` has one pure, independently-testable function per criterion (price ceiling, monthly cost, area, rooms, takeover date, encumbrance ratio), each returning `{ passed, symbol, reason, source: "ai" }` rather than a bare boolean. `renovation-category.ts` classifies A–D from BBR's build/renovation year and always comes back `isEstimate: true`/`~` unless the caller supplies a real tilstandsrapport-derived category (this endpoint never parses tilstandsrapport/elinstallationsrapport PDFs — an explicit non-goal). `symbol-engine.ts` composes the six checks into one ordered array. `config/financing-assumptions.ts` isolates every threshold (down payment, effective interest rate, grundskyld promille, per-category price ceilings, min area/rooms, encumbrance ratio ceiling, takeover deadline) behind env vars (`SCREENING_*`) so they can be tuned without touching rule logic — **all current default values are placeholders pending confirmation against the real house-buying decision rule**, called out inline with `TODO(scott)`.
- **Scoring inputs** (`apps/web/server/lib/scoring/relative-score-inputs.ts`): extracts the seven weighted-category raw inputs (location match, condition proxy, price headroom, area margin, school-district score, noise-zone estimate, legal-risk proxy) without combining them into a score — weighting stays a display-layer concern so weights are user-adjustable without a re-fetch. `locationMatch` and `schoolDistrictScore` are always `null` today; no automated source for either is wired in yet.
- **Orchestration** (`apps/web/server/lib/property-lookup/property-lookup.handler.ts`): address register → BBR + VUR + noise (in parallel) → renovation classification → screening → scoring inputs, mirroring `enrich.ts`'s pattern of letting each enrichment source gate its own mock/real split independently. The address lookup runs first and alone for two reasons: it's the only step needing no credential, and it's the geocoder — everything downstream keys off the husnummer UUID, BFE number and coordinates it resolves. An address that doesn't resolve **skips** the noise lookup rather than querying the WFS at `0,0`, which would otherwise return a confident "no noise here" for a point in the Atlantic.

Not yet done, flagged in the original planning doc as blocking or out of scope: confirming whether a Datafordeler business account already exists (BBR/OIS access is the same pending-credentials blocker documented above), confirming the real financing-assumption thresholds with Scott, and the GrunddataAPI build-vs-buy decision (would collapse `enrichment-sources/{address-lookup,bbr,ejendomsvurdering}.ts` into one client if purchased).

## Search access levels

`GET /api/properties` (`apps/web/server/lib/search.ts`) returns different shapes depending on whether the request carries a valid Supabase session (`Authorization: Bearer <jwt>`):

- **Anonymous**: only `summaries: { id, address }[]` plus the paged `total`/`limit`/`offset`/`page`/`totalPages` — enough to see how many listings match a filter and their address, nothing else. This is enforced by selecting fewer columns server-side (`search.ts`), not just hidden in the UI.
- **Signed in**: the full `properties: Property[]` array (price, sqm, images, agent, etc.), same as before.

Page size is caller-configurable (`limit`/`offset` query params, exposed in the UI as a page-size selector) up to `SEARCH_MAX_PAGE_SIZE` (default 100), which can be raised or lowered later via env var alone.

`GET /api/properties/:id` (detail: price, sold-price history, risk flags, BBR data) and `GET /api/properties/:id/comparables` require the same signed-in session — both now 401 without a valid `Authorization: Bearer <jwt>`, and the frontend's `/property/:id` route is wrapped in `AuthGuard` so anonymous visitors are redirected to sign-in before the page ever calls those endpoints. All three authenticated responses are sent with `Cache-Control: private, no-store` so a CDN can never serve one caller's data to another.
